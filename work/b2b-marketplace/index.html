PHASE 01 / CORE EXPERIENCE04 / 11

围绕商品浏览、规格配置与购物车操作，将复杂信息转化为有层级、可反馈的界面体验。

Product Center / 商品中心

设计重点

PHASE 02 / BUSINESS COMPLEXITY05 / 11

{ 当一张订单，不再对应一种简单的发货关系 }

随着订单管理需求扩展，原有以商品信息为主的展示方式，开始难以完整表达实际物流履约关系。

新增业务复杂度

01收货人、地址与物流节点

02外部订单关联

03多地址 × 多包裹

04不同型号混合发货

新增业务需求

01 物流信息完善

从仅展示物流单号，扩展为收货人、地址、包裹状态和物流节点。

02 外部订单关联

支持查看和管理与商城订单关联的外部订单号。

03 多地址与多包裹

同一订单可能涉及多个收货地址，一个地址也可能对应多个包裹。

04 混合型号发货

同一包裹可能包含多个产品型号，实际发货组合取决于库存与履约情况。

核心问题

原有商品维度的信息组织方式，无法直接覆盖所有真实发货关系。

DOMAIN MODEL / FULFILLMENT06 / 11

{ 先理解订单、包裹与地址的真实关系 }

在开始设计界面之前，先明确业务对象之间的关系，避免让页面结构建立在错误的发货假设上。

用包裹表达履约，用型号表达采购

以包裹为物流信息的主要组织单位，保留商品、地址与运输状态的关联。

INFORMATION ARCHITECTURE07 / 11

{ 从商品维度，转向包裹维度组织物流信息 }

将实际履约单位作为物流模块的核心，让用户能够理解每个包裹的内容、去向和运输状态。

BEFORE

按商品型号组织

型号 → 物流信息

分批发货与混合装箱时，分组难以反映实际包裹。
AFTER

按包裹组织

包裹 → 地址 / 商品与数量 / 状态 / 运输节点

围绕真实履约单位组织信息，保留商品可追溯性。

原有组织方式

按商品型号展示物流信息。

存在的问题

当同一型号分批发货，或不同型号混合装箱时，商品分组无法准确反映实际包裹结构。

优化后的组织方式

按包裹组织物流信息。

每个包裹下关联：

- 包裹标识与交付状态 - 收货人及收货地址 - 包裹内商品与数量 - 物流单号与运输节点

设计决策

包裹作为主要信息单位

优先呈现真实履约关系。

地址与包裹建立明确关联

减少用户在多个区域之间反复寻找信息。

商品信息保留可追溯性

让用户能够确认包裹中包含哪些型号及数量。

EXTERNAL ORDER / INTERACTION08 / 11

{ 让外部订单关联清晰可查，同时减少页面干扰 }

外部订单号是订单关联的重要业务信息，但不需要在所有场景下占据大量视觉空间。

设计问题

订单列表需要支持快速识别与查找，而订单详情需要呈现更完整的关联信息。

不同来源的外部订单号还可能具有不同的编辑规则。

设计方案

01 列表轻量展示

通过悬停弹窗查看外部订单号，减少列表常驻信息量。

02 详情集中管理

在订单详情中提供明确的信息查看与编辑位置。

03 根据来源区分操作规则

系统推送与手动录入的订单号，根据实际业务规则处理编辑权限，不增加不必要的操作。

设计重点

在信息可发现性、页面密度和操作权限之间建立平衡。

系统推送与手动录入的编辑规则须按实际业务确认；移动端交互需采用可触达的信息入口。

EDGE CASES / EXPERIENCE STATES09 / 11

{ 让设计覆盖真实业务，而不只覆盖理想流程 }

企业采购中的物流信息具有不确定性，界面需要兼容正常、拆分、缺失与异常等不同情况。

场景一：多包裹发货

一个订单拆分为多个包裹，各自具有独立物流信息。

场景二：同地址多包裹

多个包裹发往同一地址，仍需分别展示包裹状态与商品内容。

场景三：混合型号发货

一个包裹包含不同商品型号，不能简单按型号建立物流记录。

场景四：物流信息缺失

当物流单号、运输节点或其他必要数据尚未返回时，需要明确展示信息状态，避免误导用户。

场景五：物流数据异常

当返回数据存在异常时，需要区分信息不可用与正常运输状态。

以真实业务规则作为状态设计依据，让不同发货组合都能被一致、清晰地表达。

工作过程

与产品确认地址、包裹、商品及发货之间的真实关系。

02 建立交互结构

03 构建可交互原型
